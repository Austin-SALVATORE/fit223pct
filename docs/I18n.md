# Internationalization

**Status: shipped 20 Jul 2026** (Milestone 7 — see Roadmap). English,
French, and Simplified Chinese are all live-switchable from Settings;
French and Chinese content is native-reviewer-approved (see
docs/I18n-glossary-fr.md, docs/I18n-glossary-zh.md). Adding a fourth
locale is documented in docs/I18n-adding-a-locale.md. This brief remains
the spec the implementation was reviewed against — it amends the raw
feature request where that request assumed surfaces this app doesn't
have.

## Goal

Three locales at launch: English (`en`, default and fallback), French
(`fr`), Simplified Chinese (`zh-CN`). Auto-detect on first launch
(`navigator.language`), manual switch in Settings, persisted in
`UserSettings`, live switch without restart. Adding a locale later means
adding one locale file — no code changes.

## What the generic spec missed about this app

1. **The domain layer speaks.** ~30 user-facing sentences are generated
   inside `domain/` (progression reasons, adjustment reasons, driver
   labels, trend phrases, stagnation evidence, coach insights). This is
   the product's core: every claim carries its reason. i18n therefore
   requires the app's single deepest refactor: **domain functions return
   message descriptors (key + params), never prose**. The UI layer
   translates. Example: `{ key: 'progression.deferLoad' }` instead of
   "You've earned more load, but not today…". Domain stays pure and
   testable (tests assert keys, not English); copy moves to locale
   files where it belongs.
2. **Seeded data is user-facing.** Exercise names, technique cues,
   prescription notes, program and session names live in Dexie, seeded
   at first run. Locale files can't reach them. Seed content moves to
   locale-keyed lookup by stable id (`exercise.goblet-squat.name`),
   resolved at render — stored records keep ids only. Program/session
   names authored per phase are content, translated with the phase.
3. **A minimal Settings surface ships with data portability's revision
   (backup export + gear entry from Plan)** — the language switcher
   joins it rather than creating it. Original note: the switcher needs the
   app's first Settings page — minimal: a quiet header or Today-footer
   entry, language selection only. Nothing else moves into it yet.
4. **Struck from the request** (surfaces that don't exist by design —
   local-first, single-user, no server): authentication, onboarding,
   profile, success notifications. "Recovery" in the request is a
   terminology error — see below.

## Invariants (review will check these)

- **Storage stays locale-free.** IndexedDB records never contain
  translated text — ids, signal keys, tier names, message keys only.
  (The M3 driver-keys fix established this; nothing may regress it.)
- **Terminology constraints carry into every locale.** "Readiness" —
  never wellness, recovery-score, or medical vocabulary — must hold in
  French and Chinese too. Each locale file starts with a small glossary
  (readiness tiers, RIR, the five signals) agreed before bulk
  translation; translations are natural, not literal, and fitness
  terms sound like a coach, not a manual.
- **Plurals via ICU messages, not ternaries.** The five hand-rolled
  `x === 1 ? 'set' : 'sets'` sites migrate; French pluralizes
  differently and Chinese doesn't pluralize at all.
- **Dates and numbers via `Intl`** with the active locale
  (`formatLongDate`, evidence dates, units). Units stay metric.
- **Fallback is English** for any missing key; a missing key in dev is
  a console error, never silent.
- **User content is never translated — and never shadowed by
  translation.** The app translates itself, not your data. The one
  seeded program's name/session/note fields resolve through a locale
  key (`resolveSeedString`-style fallback in `src/i18n/seedProgram.ts`);
  a user's own imported program never does, even if it reuses the
  seed's id — `Program.origin` (`'seed' | 'imported'`) makes that
  explicit rather than inferring it from id, after real use found an
  id-only fallback silently replacing authored notes with the seed's
  translated ones (docs/DataPortability.md, 20 Jul fix).

## Implementation shape

- **Library**: react-i18next (battle-tested, live switching, ICU via
  plugin, TS-typed keys) — confirm with a short eval at kickoff before
  committing.
- **Locale files**: `src/locales/{en,fr,zh-CN}/` split by module
  (`domain.json`, `today.json`, `workout.json`, `progress.json`,
  `library.json`, `checkin.json`, `common.json`, `seed.json`).
- **Order of work**: descriptor refactor in domain (with tests moved to
  keys) → extract feature-component strings → seed-content lookup →
  Settings page + detection/persistence → French → Chinese → docs on
  adding a locale.
- **`<html lang>`** updates with the locale; the a11y audit's focus
  and title handling already exists and must announce in the active
  language.

## Acceptance

Switching language updates every visible string without reload; all
three locales complete; English fallback proven by removing a key in
dev; stored data unchanged byte-for-byte before/after a language
switch; glossary reviewed by a native reader per locale before ship.

## Two guards, because one class was invisible — 30 Jul

**`localeParity.test.ts` compares every locale to `en`. Nothing was
comparing `en` to the code.** So an fr-only or zh-only omission is
structurally impossible while parity is green, and a key missing from
*all three* is invisible to it, because the reference is one of the
things being checked.

`common:cancel` lived in that hole from M10 phase 3 until 30 Jul. The
profile form's Cancel button rendered the literal lowercase key path in
every language, and it surfaced only because a device check happened to
read the browser console. Parity was green the whole time, correctly.

`translationKeys.guard.test.ts` closes it: every literal `t()` /
`tCommon()` key in `src/**` must resolve in an `en` bundle its file
loads, and a failure names the file, line and key. Keep both — they
catch different classes, and folding them together would restore the
gap.

Its two limits are stated in the file and are deliberate:

- **Computed keys are excluded** — ``t(`activityName.${level}`)``
  cannot be resolved statically. Covered instead by rendering tests
  that assert resolved strings, plus the device pass. A test asserts
  the exclusion is real, so it cannot be quietly simplified away.
- **A key resolving in *any* namespace its file loads passes**, so a
  key in the wrong namespace of a two-namespace file is not caught.
  The target is "declared nowhere"; a false positive that blames
  innocent code is how a guard gets deleted.

**The first version of this guard passed while checking nothing** — an
alias-parsing regex whose `const …useTranslation` alternative won
leftmost-match over `t: tCommon`, capturing no alias, after which every
`tCommon(...)` call was discarded as not-a-translator. It went green
with `common:cancel` deleted: blind to the exact bug it was written
for, and caught only by a negative control. **A guard is not evidence
until it has been made to fail on purpose.**

## Mesocycle 2 English placeholders — 6 Aug 2026, dated

Six new Library exercises (`push-up`, `dumbbell-fly`, `dumbbell-pullover`,
`chest-supported-row`, `hamstring-walkout`, `standing-calf-raise` —
Mesocycle-2-Home-Progressive-Coach-Spec-v2.7.md §18) ship with **the same
English `name`/`cues`/`teachingConcept` text seeded into all three locale
`seed.json` files**, not just `en`. This is not the seed-clobber bug —
it is deliberate, and it is the owner's ruling communicated through the
coach's spec §3: ship English everywhere rather than machine-translate
coaching language under deadline, or slip the 10 Aug start date.

**French and Chinese are due no later than Sunday 16 August 2026**
(spec §3, restated by the coach on review of v2.7). Until then, the
French and Chinese apps show English coaching cues for these six
exercises specifically — visible in the UI as English text mixed into
an otherwise-translated screen, not a blank or a raw key, so the gap is
legible to anyone reading the screen rather than silent.

`localeParity.test.ts` stays green throughout: identical keys exist in
all three files, satisfying key-family parity by construction. Parity
proves every locale *declares* the same keys; it was never able to
prove the *values* differ, so this placeholder is invisible to it by
design, not by accident. When the real French and Chinese text lands,
replace these six entries' content only — the keys and structure
already match every other Library exercise, so no schema or code
change is needed, just a content commit through the normal seed path.

Same treatment, lower stakes: the `mesocycle-2-build` program's own
name and its three session names/focus strings (`program.mesocycle-2-
build.*` in `seed.json`) carry the same English text in all three
locales for the same reason. These aren't coach-authored coaching
language — short UI labels ("Chest & Back", "Legs and Core Emphasis")
— but they're seeded through the same path and covered by the same 16
Aug date for consistency.

**Correction, 6 Aug review.** An earlier version of this note said
per-prescription `note` fields (rest-range and progression annotations,
e.g. "Rest after both sides") were deliberately left unkeyed, falling
back to the stored English literal like an imported program does. That
was wrong on two counts: `phase-1-home` — also seed-origin — already
has ten translated `note` keys across the three locale files, so there
was direct in-repo precedent for keying these, not following it. And
the fallback path makes the gap *invisible* rather than visible — the
owner's ruling was specifically for English placeholders written into
every locale file so a translator scanning `fr/seed.json` sees English
text and knows there is work to do. A key that does not exist in any
locale leaves nothing to compare, so `localeParity.test.ts` cannot see
it either; parity stayed green with no key at all, for the same
structural reason it stays green on a wrong value (see above). Fixed:
all seven prescription notes on `mesocycle2Build` (`program.mesocycle-
2-build.session.<id>.exercise.<exerciseId>.note`) now carry the same
English text in all three locale files, same 16 Aug date.

## Out of scope (deliberate)

RTL support (no RTL locale planned), per-locale content differences,
translating past data (there is none — storage is locale-free), server
locale negotiation (no server).
